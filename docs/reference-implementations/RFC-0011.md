# RFC-0011 — Reference Implementation

Implements: [RFC-0011 — The Deterministic Reasoning Engine](../../docs/rfcs/0011-deterministic-reasoning-engine.md)

This document explains **how** RFC-0011 is implemented. It is not the
specification; the RFC remains the canonical definition (Engineering
Principle #11). This guide evolves with the code and answers:

- Why each module exists.
- How each module maps to the RFC.
- Design decisions and their trade-offs.
- Known limitations.
- Future extensions.

## Goal Extractor

**RFC mapping:** RFC-0011 §1.1; input `Intent`, output `Goal[]`.

### Design decisions

1. **Structured goals win.** `intent.goals` (RFC-0005 §2) is the
   authoritative source. Text extraction only runs when no structured goals
   exist. A human explicitly stating goals must never have them overridden
   by an inference.
2. **Lexicon, not NLP.** `VERB_LEXICON` maps a fixed set of verbs
   (`open`, `send`, `toggle`, ...) to goal kinds. There is no stemming, no
   synonyms, no model.
3. **No guessing.** An unknown verb yields zero goals, which the engine
   reports as `clarificationRequired`. Refusing to invent goals is the
   trustworthiness property (RFC-0011 §3).
4. **Target extraction is positional.** The remainder of the phrase after
   the verb becomes `Goal.target` ("Open Settings" → kind `openApp`,
   target `Settings`). This keeps the goal structured for future planners
   instead of baking the target into a description string.

### Known limitations

- One verb phrase per text; compound intents must use structured goals.
- "reply to Alice" keeps the preposition ("to Alice") as target. A future
  cleanup pass could strip leading prepositions.
- Multi-word verb phrases (e.g., "turn on") are not supported yet.

### Future extensions

- Preposition handling ("to", "in") for cleaner targets.
- Multi-verb phrase splitting into multiple goals (with ordering).

## Constraint Checker

**RFC mapping:** RFC-0011 §1.2; RFC-0007 §Core Concepts (categories).

### Design decisions

1. **RFC-0007 categories drive enforcement.** The contract's `Constraint`
   carries `category`: `hard` (must hold), `soft` (preference), `safety`
   (non-negotiable), `temporal` (time-bound), `resource` (consumption
   limits). The checker's semantics differ per category.
2. **Safety is never overridable.** A `forbid` constraint of category
   `safety` rejects the goal regardless of any `allow` — the platform must
   not permit policy bypass.
3. **Hard forbid yields to explicit allow.** An `allow` constraint on the
   same goal kind cancels a `hard` forbid (explicit user override wins over
   a default policy).
4. **Soft constraints never reject.** They are preferences; the deterministic
   engine has no optimizer yet (RFC-0011 §6: soft constraints are not
   evaluated). A future Plan Optimizer stage consumes them.
5. **Temporal and resource constraints are declared, not evaluated.** The
   engine has no clock or budget at reasoning time; they bind at execution.
   The checker acknowledges them without rejecting.

### Known limitations

- No target-aware constraint matching yet (a constraint cannot yet say
  "forbid only for contact Alice"); matching is by goal kind only.
- No priority resolution between conflicting allows/forbids beyond the
  allow-overrides-hard rule.

### Future extensions

- Target-scoped constraints (`goal.target` matching).
- Constraint conflict detection and priority (RFC-0007 §conflicts).
- Weighted soft constraints for the Plan Optimizer.

## Capability Matcher (skeleton)

**RFC mapping:** RFC-0011 §1.3.

- Reasons over **CapabilityDescriptors** (id, goalKinds, description) —
  never over runtime Capability objects with `execute`. The engine must not
  know `driver.launch()`.
- Current logic: first capability whose `goalKinds` includes the goal kind.
- Future: resource availability, declared permissions, descriptor scoring.

---

## Plan Builder (skeleton)

**RFC mapping:** RFC-0011 §1.4.

- One sequential `PlanStep` per goal, ordered by goal declaration order,
  with linear `dependsOn` chains.
- Future: parallel steps for unordered goals (RFC-0005 §2: Ordered or
  unordered), capability-provided step details.

---

## Plan Validator (skeleton)

**RFC mapping:** RFC-0011 §1.5; RFC-0006 invariants.

- Enforces: non-empty steps, registered capability ids, unique step ids,
  valid `dependsOn` references.
- The platform's authority: an invalid plan never leaves the engine.

---

## Engine Orchestration

**RFC mapping:** RFC-0011 §2, §3; RFC-0009 §2.

- Composes the five stages in order; each stage injectable via
  `EngineComponents` so an RFC-0012 (LLM) backend can replace individual
  stages later.
- Result contract (RFC-0009): `executionPlan` | `clarificationRequired` |
  `rejected`, with deterministic guarantees (same input → same output, no
  I/O, no hidden state).

---

## Design Decisions That Apply Package-Wide

1. **No I/O, ever.** The engine performs no network, no device access, no
   model calls. All data arrives via the Intent and the CapabilityRegistry.
2. **Stages are pure.** Each stage has one input, one output, no side
   effects. Tests therefore need no mocks beyond a fake registry.
3. **Deterministic by construction.** No randomness, no timestamps in
   outputs, no iteration order dependence. Tests assert exact equality.
4. **One concept, one definition.** Stage interfaces are local to the
   package; shared contracts live in core. Nothing leaks from lower layers.

---

## Known Package-Wide Limitations

- No Context/Resource/Trigger handling yet (RFC-0005 §4–§6) — the engine
  reasons over Intent alone.
- No Decision Points (RFC-0008) — those belong to execution.
- No recovery planning (RFC-0005, Recovery) — a failed goal fails the
  intent.

---

## Future Extensions

1. **Plan Optimizer stage** (between Capability Matcher and Validator):
   consumes soft constraints and produces preferred orderings. Per the
   architecture review, optimization is a separate stage, never inside Plan
   Builder.
2. **Simulation stage** (between Validator and output): answers "what will
   happen if I execute this?" before execution.
3. **RFC-0012 LLM backend:** replaces the Goal Extractor behind its
   interface; Validator remains the authority.
