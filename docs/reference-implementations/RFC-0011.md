# RFC-0011 — Reference Implementation

Implements: [RFC-0011 — The Deterministic Reasoning Engine](../../docs/rfcs/0011-deterministic-reasoning-engine.md)

This document explains **how** RFC-0011 is implemented. It is not the
specification; the RFC remains the canonical definition (Engineering
Principle #11). This guide evolves with the code and answers:

- Why each module exists.
- How each module maps to the RFC.
- Design decisions and their trade-offs.
- Known limitations.
- Future extensions.

## Goal Extractor

**RFC mapping:** RFC-0011 §1.1; input `Intent`, output `Goal[]`.

### Design decisions

1. **Structured goals win.** `intent.goals` (RFC-0005 §2) is the
   authoritative source. Text extraction only runs when no structured goals
   exist. A human explicitly stating goals must never have them overridden
   by an inference.
2. **Lexicon, not NLP.** `VERB_LEXICON` maps a fixed set of verbs
   (`open`, `send`, `toggle`, ...) to goal kinds. There is no stemming, no
   synonyms, no model.
3. **No guessing.** An unknown verb yields zero goals, which the engine
   reports as `clarificationRequired`. Refusing to invent goals is the
   trustworthiness property (RFC-0011 §3).
4. **Target extraction is positional, with preposition cleaning.** The
   remainder of the phrase after the verb becomes `Goal.target` ("Open
   Settings" → kind `openApp`, target `Settings`). Leading prepositions
   ("reply **to** Alice") are stripped so constraints can target-match on
   the bare name. This keeps the goal structured for future planners
   instead of baking the target into a description string.

### Known limitations

- One verb phrase per text; compound intents must use structured goals.
- Multi-word verb phrases (e.g., "turn on") are not supported yet.

### Future extensions

- Multi-verb phrase splitting into multiple goals (with ordering).

## Constraint Checker

**RFC mapping:** RFC-0011 §1.2; RFC-0007 §Core Concepts (categories).

### Design decisions

1. **RFC-0007 categories drive enforcement.** The contract's `Constraint`
   carries `category`: `hard` (must hold), `soft` (preference), `safety`
   (non-negotiable), `temporal` (time-bound), `resource` (consumption
   limits). The checker's semantics differ per category.
2. **Safety is never overridable.** A `forbid` constraint of category
   `safety` rejects the goal regardless of any `allow` — the platform must
   not permit policy bypass.
3. **Hard forbid yields to explicit allow.** An `allow` constraint on the
   same goal kind cancels a `hard` forbid (explicit user override wins over
   a default policy).
4. **Soft constraints never reject.** They are preferences; the deterministic
   engine has no optimizer yet (RFC-0011 §6: soft constraints are not
   evaluated). A future Plan Optimizer stage consumes them.
5. **Temporal and resource constraints are declared, not evaluated.** The
   engine has no clock or budget at reasoning time; they bind at execution.
   The checker acknowledges them without rejecting.

### Known limitations

- No target-aware constraint matching yet (a constraint cannot yet say
  "forbid only for contact Alice"); matching is by goal kind only.
- No priority resolution between conflicting allows/forbids beyond the
  allow-overrides-hard rule.

### Future extensions

- Target-scoped constraints (`goal.target` matching).
- Constraint conflict detection and priority (RFC-0007 §conflicts).
- Weighted soft constraints for the Plan Optimizer.

## Capability Matcher

**RFC mapping:** RFC-0011 §1.3.

### Design decisions

1. **Candidates, not uniqueness.** `matchGoals` returns **every** matching
   capability per goal (`GoalCapabilityOptions.candidates`), each with a
   reason. A goal like "Open Camera" legitimately matches both
   `launch_app` and `activate_existing_app`; the matcher must not hide that.
2. **Selection is a separate function.** `selectCapabilities` picks one
   candidate per goal (first in registry order today). A future Plan
   Optimizer replaces this function — the interface stays, the choice
   improves. This is the RFC-0012/optimizer seam.
3. **Descriptors only.** The matcher reasons over `CapabilityDescriptor`
   (id, goalKinds, description) — never over runtime Capability objects
   with `execute`. The engine does not know `driver.launch()`.
4. **Explained choices.** Every candidate carries a reason ("capability
   'launch_app' declares goal kind 'openApp'"), keeping selection
   auditable.

### Known limitations

- No resource availability or permission checks at matching time.
- No preference scoring (soft constraints are not consumed here).

### Future extensions

- Preference-aware selection for the Plan Optimizer.
- Registry-supplied availability metadata.

## Plan Builder

**RFC mapping:** RFC-0011 §1.4.

### Design decisions

1. **Explicit bindings.** The builder consumes `bindings` (goal ↔
   capability pairs), never two parallel arrays — no index coupling
   between goals and capabilities.
2. **Stupid by design.** One sequential `PlanStep` per binding, in binding
   order, with linear `dependsOn` chains. No optimization, no search, no
   retries. Assembly only.

### Known limitations

- No parallel steps for unordered goals (RFC-0005 §2: Ordered or unordered).
- No capability-provided step detail (actions, arguments) — steps carry a
  generic `action: 'execute'`.

### Future extensions

- Parallel steps for independent goals.
- Capability-declared action/argument templates.

## Plan Validator

**RFC mapping:** RFC-0011 §1.5; RFC-0006 §Plan Invariants, §Validity Rules.

### Design decisions

1. **Compiler-like diagnostics, not pass/fail.** `validatePlan` returns
   `valid`, `errors`, `warnings`, `suggestions`, and a `trace` of every
   check run (code + outcome). Errors invalidate; warnings and suggestions
   inform without blocking. This is what makes Athena explainable: a plan
   consumer can say *why* a plan failed, not just that it failed.
2. **Never mutates.** The validator is a pure function over
   `(plan, registry)`. It reports; it never rewrites. Suggestion is
   advisory by design (no auto-fix), preserving the separation between
   reasoning, validation, and execution.
3. **Structural/semantic phase seam.** Diagnostics carry a `phase` field.
   `structural` (current) checks RFC-0006: `PLAN_EMPTY`,
   `STEP_DUPLICATE_ID`, `STEP_UNKNOWN_CAPABILITY`,
   `STEP_UNKNOWN_DEPENDENCY`, `PLAN_CYCLIC` (errors);
   `STEP_OUT_OF_ORDER` (warning); `STEP_TRANSITIVE_DEPENDENCY`
   (suggestion). `semantic` (RFC-0006 §4–§8, RFC-0007, RFC-0008,
   RFC-0009) is declared but unimplemented — the same seam a compiler has
   between parse and type check.
4. **Every future backend passes through it.** Deterministic or LLM
   (RFC-0012), a plan is not an Execution Plan until this validator accepts
   it (RFC-0009: the contract includes validation, not just generation).

### Known limitations

- Capability parameter/schema validation (RFC-0006 §2) is not yet
  implemented — steps carry only `action: 'execute'`.
- No goal-coverage (RFC-0006 §4), constraint-compliance (RFC-0006 §5),
  decision-point (RFC-0006 §6), recovery (RFC-0006 §7), or determinism
  (RFC-0006 §8) checks — these are the `semantic` phase.

### Future extensions

- The `semantic` validation phase (the open door).
- Capability input-schema validation against step arguments.
- A diagnostics formatter for human/CLI consumption.

## Simulation

**RFC mapping:** RFC-0011 §1.6; RFC-0005 §5 (Resources), RFC-0009
(Confidence; input: Environment).

### Design decisions

1. **Predicts, never executes.** The simulator performs no I/O and no
   device access; it cannot run a capability. It answers "what would
   probably happen" from declared facts only — the same honesty contract
   as the validator, before anything touches the device.
2. **Deterministic and derived from the registry only.** Outcome spectrum
   (`success` / `likely_success` / `likely_failure` / `failure` /
   `unknown`) comes from `availability`, `requiresResources` vs the
   `SimulationEnvironment`, and `reliability`:
   - declared `unavailable` → `failure`, confidence 0, added to `blocked`;
   - missing declared resources → `likely_failure`, confidence halved;
   - no declared reliability → honest `unknown` (0.5), never optimism.
3. **Advisory, not authoritative.** Simulation never rejects a plan and
   never blocks execution: `blocked` and `warnings` inform the platform
   (RFC-0008 decision points) but validity remains the validator's call.
4. **Runs after validation.** An invalid plan never reaches simulation,
   keeping the trust boundary sharp: the validator decides; the simulator
   advises.
5. **Splits no opinions.** Per-step reasons are collected in plain strings
   so a human or CLI can read why a step is predicted to fail — same
   explainability goal as validator diagnostics.

### Known limitations

- Predictions are trust-only: they cannot see real device state, so
  `available` + declared reliability still allows surprise at runtime.
- `conditional` availability is treated as likely-success with declared
  reliability — approval likelihood is not modeled (RFC-0008 belongs to
  execution).
- No step dependency-chain reasoning: a step blocked by a failed
  prerequisite is not yet marked likely_failure.

### Future extensions

- Dependency-aware prediction (propagate failures down `dependsOn`).
- Execution-result feedback loop (learning RFCs) to calibrate
  per-capability reliability from real outcomes.
- A simulator backend for RFC-0012 plans — same interface, same
  trust-only contract.

## Engine Orchestration

**RFC mapping:** RFC-0011 §2, §3; RFC-0009 §2.

- Composes the six stages in order; each stage injectable via
  `EngineComponents` so an RFC-0012 (LLM) backend can replace individual
  stages later.
- Result contract (RFC-0009): `executionPlan` | `clarificationRequired` |
  `rejected`, with deterministic guarantees (same input → same output, no
  I/O, no hidden state).

---

## Design Decisions That Apply Package-Wide

1. **No I/O, ever.** The engine performs no network, no device access, no
   model calls. All data arrives via the Intent and the CapabilityRegistry.
2. **Stages are pure.** Each stage has one input, one output, no side
   effects. Tests therefore need no mocks beyond a fake registry.
3. **Deterministic by construction.** No randomness, no timestamps in
   outputs, no iteration order dependence. Tests assert exact equality.
4. **One concept, one definition.** Stage interfaces are local to the
   package; shared contracts live in core. Nothing leaks from lower layers.

---

## Known Package-Wide Limitations

- No Context/Trigger handling yet (RFC-0005 §4, §6) — the engine reasons
  over Intent and the declared Environment, not live context.
- Environment resources are declared fact; no real capability-state probe.
- No Decision Points (RFC-0008) — those belong to execution.
- No recovery planning (RFC-0005, Recovery) — a failed goal fails the
  intent.

---

## Future Extensions

1. **Plan Optimizer stage** (between Capability Matcher and Validator):
   consumes soft constraints and produces preferred orderings. Per the
   architecture review, optimization is a separate stage, never inside Plan
   Builder.
2. **Semantic validation phase** (RFC-0011 §1.5): the validator's
   `semantic` door — RFC-0006 §4–§8 invariants, RFC-0007 constraint
   compliance, RFC-0008 decision points, RFC-0009 reasoning guarantees.
3. **RFC-0012 LLM backend:** replaces the Goal Extractor behind its
   interface; Validator remains the authority.
